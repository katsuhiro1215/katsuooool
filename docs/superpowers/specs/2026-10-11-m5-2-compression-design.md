# M5-2: 圧縮方式の比較と採否 設計書

ステータス: 実装済み（`docs/superpowers/plans/2026-10-11-m5-2-compression.md`）。本番反映は未実施。

作成日: 2026-10-11 / ブランチ: `feature/m5-2-compression` / 対象: ロードマップ M5 の第2段階（M5-1 上限、M5-3 画面とリサイズは別設計）

## 1. 目的

画像圧縮の精度（同じ見た目でより小さく）を上げる。cwebp・pngquant・oxipng・jpegoptim・avifenc を、現行の Imagick 方式と、**圧縮率・見た目・速度・メモリ**で比較し、採否を決める。あわせて「CLI バイナリに依存しない」方針（M2 以来）を変えるかを決める。

## 2. 比較の方法（2026-10-11 実施）

- 環境: 本番相当（CPU 2・メモリ 768MB）の使い捨てコンテナ。Imagick の制限は M5-1 の値。
- 素材: オーナーの写真 2 枚（カメラ JPEG 18MP、iPhone 12MP）、ChatGPT 生成の PNG 5 枚と image1.png（イラスト系）、本番サイトのスクリーンショット 4 枚、WebP（上の写真から作成、18MP・12MP）。
- 画質: ssimulacra2（0〜100。高いほど元に近い。90 以上はほぼ見分けがつかず、70 台は注意して見ると差がわかる）。ICC プロファイルを sRGB に変換してから比較。
- 時間・メモリ: コンテナ内で計測（メモリは cgroup のピーク）。
- 比較用のスクリプトと画像は `scratchpad` に置き、リポジトリには入れない。

## 3. 結果

### 3.1 PNG（採用を推奨：pngquant）

平均値（サイズは元に対する割合）:

| 方式 | AI/イラスト 6枚 サイズ | 画質 | 時間 | メモリ | スクショ 4枚 サイズ | 画質 | 時間 |
|---|---|---|---|---|---|---|---|
| 現行（256色化→小さい方） | 36.4% | 67.5 | 4.9秒 | 236MB | **97.5%** | 89.7 | 1.7秒 |
| pngquant 65-80 | 30.4% | 67.9 | 1.4秒 | 45MB | 23.0% | 82.2 | 0.2秒 |
| pngquant 80-95 | 36.7% | 74.1 | 1.2秒 | 44MB | 28.7% | 86.4 | 0.2秒 |
| oxipng 無劣化 | 91.8% | 100 | 3.5秒 | 30MB | 78.7% | 100 | 1.1秒 |
| pngquant 80-95 + oxipng | 33.6% | 74.1 | 2.3秒 | 45MB | 27.2% | 86.4 | 0.7秒 |

- **現行は UI のスクリーンショットをほとんど縮められない**（97.5%）。文字中心の画像では、元より大きくなった（57KB が 66KB）。pngquant なら同程度の画質で約 25〜29%。
- イラスト系でも、同じサイズなら pngquant のほうが画質が高い（例: png-ai-3 は現行 643KB・画質 64.7、pngquant 80-95 は 571KB・画質 71.0）。
- pngquant は現行より約 4 倍速く、メモリは約 1/5。
- oxipng（無劣化）は、イラスト系で約 8%、スクショで約 21% 縮む。画質が変わらないので「控えめ」の水準に向く。pngquant との併用で、さらに 4〜8% 縮むが、時間が +0.7〜1.4 秒。

### 3.2 JPEG（jpegoptim を推奨。ただし EXIF の扱いに判断が必要）

- 画質が同じなら、Imagick（現行・調整版）と jpegoptim の曲線は、ほぼ重なる。**圧縮率の優位はない。**
- **現行のサービスは、すでによく圧縮された JPEG を大きくする**（カメラ JPEG 4.26MB が q80 で 4.73MB、113.6%）。ただし、コントローラーに「元より大きければ元を返す」処理が既にあるため、利用者には 0% として表示される。
- jpegoptim は、品質を上限として扱うので（`--max`）、元より高い品質には上げず、**大きくならない**。無劣化モードは、画質 100（ICC 保持時）のまま 4〜7% 縮む。
- jpegoptim は約 2 倍速く、メモリは約 1/3（18MP で 124MB、現行は 355MB）。
- **注意（ICC）**: `--strip-all` は ICC プロファイルを消し、iPhone の写真（Display P3）の色が変わる（画質 100→88.7）。ICC を残す設定にする。
- **注意（EXIF）**: `--strip-exif` は向き（Orientation）まで消し、縦向きの写真が横倒しになる（確認済み）。向きを残す設定（`--strip-com --strip-iptc --strip-xmp`）では **GPS などの EXIF も残る**（iPhone の写真には GPS が入っている）。現行は再エンコードで EXIF を捨てるので GPS が消えている。→ 判断が必要（§5）。

### 3.3 WebP（cwebp を推奨：メモリ）

- 同じ品質値での出力は、Imagick と cwebp でほぼ同一（同じ libwebp）。
- **メモリが大きく違う**: 18MP の WebP を再圧縮すると、Imagick は**ピーク 768MB（コンテナの上限そのもの）**、cwebp は 143MB。12MP で 658MB 対 80MB。M5-1 で測った WebP 変換（JPEG から。213MB）とは別の経路で、WebP 入力の圧縮は、現行でも本番で落ちる恐れがある。
- cwebp は約 1.2 倍速い。`-m 6` は約 4〜5% 小さくなるが、約 30% 遅い。
- 画質の目盛り: q75 で画質約 70、q80 で約 75、q85 で約 81。

### 3.4 AVIF（変更なし。CLI は不要）

- 同じ画質で並べると、Imagick と avifenc は同じ曲線の上にある（Imagick q80: 676KB・63.2、avifenc q55: 840KB・68.4、q45: 571KB・57.1）。メモリも同程度（12MP で 410〜460MB）。
- Imagick の `heic:speed=8` で約 3 倍速くなる（12MP: 9.3秒→3.3秒、画質の低下は約 1）。メモリは変わらないので、M5-1 の AVIF の画素数の上限（800万画素）は据え置く。

## 4. 推奨

| 形式 | 推奨 | 理由 |
|---|---|---|
| PNG | **pngquant を採用**（控えめ=oxipng 無劣化も） | 同画質で約 4 倍速く、メモリ約 1/5。スクショで約 3.5 倍小さい |
| JPEG | **jpegoptim を採用**（ICC を保持） | 大きくならない。2 倍速く、メモリ約 1/3。圧縮率は同等 |
| WebP | **cwebp を採用**（`-m 4`） | 出力は同じで、メモリが約 1/5〜1/8。本番で落ちる恐れを解消 |
| AVIF | 現行の Imagick のまま。`heic:speed` を 8 に | CLI の優位なし。3 倍速くなる |

- **方針の変更**: 「CLI バイナリに依存しない」を、圧縮については改める。理由は、上の通り、圧縮率・速度・メモリのすべてで有利で、現行の欠点（スクショが縮まない、JPEG が大きくなる、WebP でメモリが尽きる）を直せるため。
- **フォールバック**: CLI が見つからない環境（ローカル開発・テスト）では、現行の Intervention（Imagick/GD）の方式に戻す。M2 以来の「GD フォールバック」の方針は維持する。旧 Xserver は M7 で停止するため、本番の制約にはならない。
- **サイズの保証**: 出力が元より大きいときに元を返す処理は、コントローラーに既にある（変更なし）。
- **圧縮レベル（3 段階）**: バックエンドで `level` を受け取れるようにする（画面の選択は M5-3）。案:
  - 控えめ（無劣化）: PNG は oxipng、JPEG は jpegoptim 無劣化、WebP は q90
  - 推奨: PNG は pngquant 80-95、JPEG は jpegoptim `--max=85`、WebP は q80
  - 強め: PNG は pngquant 65-80、JPEG は jpegoptim `--max=75`、WebP は q75
  - pngquant が品質下限を満たせず終了コード 99 を返したときは、oxipng 無劣化に落とす。

## 5. 決定（2026-10-11、オーナー確認済み）

- **方針の変更（CLI の採用）: 承認。** 圧縮については「CLI バイナリに依存しない」を改める。CLI が無い環境では現行の方式にフォールバックする。
- **JPEG の EXIF: (a) 残す。** 向きを守るため、`jpegoptim` は `--strip-com --strip-iptc --strip-xmp` のみを使う（`--strip-exif` と `--strip-all` は使わない）。GPS が残るため、画面（M5-3）と圧縮後の結果欄に「位置情報（GPS）は残ります」と注記する。

（以下は、判断の際の資料）

1. **方針の変更（CLI の採用）をよいか。**
2. **JPEG の EXIF の扱い。** 向きを残すと GPS も残る（現行は GPS が消える）。選択肢:
   - (a) EXIF を残す（向きは安全、GPS が残る）。画面に「位置情報が残ります」と表示する。
   - (b) 向きを画素に反映してから EXIF を消す（`jpegtran` の無劣化回転が追加で必要。GPS が消える。実装が増える）。
   - (c) JPEG は Imagick の再エンコードのまま（GPS が消える。圧縮率は同じ。メモリが大きく、元より大きくなる場合はサイズの保証で元を返す）。

## 6. 実装の範囲（承認後）

- Dockerfile.prod に `pngquant`・`oxipng`・`jpegoptim`・`libwebp-tools` を追加（約 5MB 増）。
- `ImageCompressService` を、形式ごとの「CLI 実行」＋「フォールバック」＋「サイズの保証」に書き換える。CLI の実行は `Symfony\Component\Process` で、タイムアウトと一時ファイルの掃除を行う。
- 既存の枚数・画素数・同時実行の制限（M5-1）はそのまま。PNG の「256色化は 250万画素まで」の制限は、pngquant では不要になる（25MP でも速いかを確認する）。
- テスト: 形式ごとの出力サイズの比較、ICC・向きの保持、サイズの保証、フォールバック、pngquant の終了コード 99。

## 7. やらないこと

- AVIF への CLI の導入。
- mozjpeg（Alpine に標準パッケージがない）。
